# Giftory（ギフトリー）要件定義書

## 1. 概要

Giftoryは、家族や友人に贈った品物と相手の反応を記録し、次に贈るものを選ぶときに相手別に見返せるWebアプリである。

開発のきっかけは、自分が過去に誰に何を贈ったかを忘れ、次のプレゼント選びで困った経験である。贈った後に短い記録を残し、翌年の誕生日や記念日に「前回は何だったか」「相手はどう使っていたか」を確かめられるようにする。1人で利用を始められ、必要に応じて特定の相手の履歴だけを夫婦や友人で共有する案を検証する。

公開URLは最終提出時に記載する。現時点では企画・要件定義段階である。

## 2. ビジネス要件

### 2.1 顧客セグメントとアーリーアダプター

対象は、誕生日や記念日などに同じ家族・友人へ繰り返し贈り物をし、選ぶ前に過去の内容を確かめたい人である。最初の利用対象を開発者本人1人と、同じ相手への贈り物を一緒に選ぶ身近な協力者1人の計2人と仮定する。この人数は試用の計画値であり、協力者の参加は未確定である。広い市場の人数は未推計。初回は本人の周囲でこの利用場面がある人数を聞き取り、対象の見積もりを更新する。

贈られる相手は会員登録不要。企業の贈答品管理、販売店の顧客管理、一度限りの贈答を記録する人は初期の対象外とする。

### 2.2 課題と既存の代替手段

| 課題 | これまでに分かっていること | 現在の対処方法と確認点 |
|---|---|---|
| 次に贈るとき、前回の品物を思い出せない | 開発者本人が経験した課題。前回の内容が分からず、今回の候補を決めにくい | 記憶、写真、メッセージ、購入履歴などが代替手段の候補。直近の贈り物を例に、本人が実際に何を見て探したかを記録する |
| 一緒に選ぶ人が、相手にすでに贈った品物や反応を確認しづらい | 夫婦・友人で履歴を共有したいという開発者の要望。第三者の困り方は未確認 | その場で相手に聞く、過去のやり取りを見返すなどが候補。共同で選んだ直近の場面を協力者に聞く |

### 2.3 独自の価値提案

毎年同じ人への贈り物を考える人が、相手の名前を開くだけで、前回贈った品物とその後の反応を一緒に確かめられる。

写真は見た目を、購入履歴は購入した商品を確かめるのに使える。Giftoryでは「誰に・いつ・何を贈ったか」に反応を結び付けるため、購入日や店名を覚えていなくても、贈る相手を起点に振り返れる。共有時も、他の相手の記録は個人用のまま使える。

### 2.4 ソリューション

1. 相手を登録し、贈った後に品物名・日付・贈った人を入力する。反応は後から追記できる。
2. 次の贈り物を選ぶ前に相手を開くと、新しい順に履歴が並ぶ。品物と反応を読み、同じ品を避けるか、喜ばれた品を再び選ぶかを本人が判断する。
3. 共同利用が必要な場合は、その相手に限って招待する。参加者同士が同じ履歴を見て、自分が贈った品も追記できる。共有を初回試用に含めるかはレビューで決める。

### 2.5 チャネル・収益・コスト

最初は開発者から家族または友人に直接、公開URLと使い方を案内する。初期版は無料とし、広告・課金は設けない。個人利用の価値は1人で確かめられる。共有の価値を確かめるには同じ相手を知る2人が必要なため、本人を含む1組を最初の試用目標とする。登録人数に加え、次の贈り物を決める場面で履歴が実際に使われたかを成功の判断に使う。

インフラ・DB・ドメインの予算は0円。カード登録不要の無料プランでAPI・画面・DBを公開する。写真を保存する場合は容量と無料枠の条件も確認する。見本には自作素材か利用条件を確認した素材を使い、利用者には掲載する権利のある写真を登録してもらう。

### 2.6 主要指標と検証

以下は実施前の検証計画である。各回で実施日・対象者（本人／協力者）・操作結果・迷った点を記録し、第三者の氏名は残さない。

| 仮説 | 確かめ方 | 初期の判定基準案 |
|---|---|---|
| 相手別の履歴から、前回の品物を探し出せる | 過去の贈り物を複数登録し、普段の方法とGiftoryで前回の品物を探す。発見可否・所要時間・手掛かりを記録する | 本人が補助なしで正しい記録を開ける。普段の方法との差と、時間がかかった理由を説明できる |
| 記録の手間が小さければ続けて使える | 贈り物1件の登録時間と迷った項目を記録。後日に別の品を登録するかを確認する | 必須項目だけで登録を完了でき、別の日にも自分で記録を追加できる |
| 履歴が次の選択に役立つ | 実際に贈り物を選ぶ際、どの記録を読み、候補を残したか・外したかとその理由を聞く | 過去の品物または反応が判断に役立った実例を1件記録する |
| 共有により、2人が同じ記録を確認できる | 共有を採用した場合、1組で招待・参加し、同じ相手の履歴と各自の個人用履歴を確認する | 2人とも共有相手と公開範囲を正しく説明し、相手に尋ね直さずに同じ記録を特定できる |

試用期間中に実際の贈答機会がなければ、模擬操作の結果と実生活での効果は分けて記録する。最終提出時に実測値、利用者の意見、変更した点と理由、変更しなかった点と理由を本節に追記する。

### 2.7 圧倒的な優位性

現時点で、競合が模倣しにくい技術や独占データはない。写真アルバムやメッセージアプリは幅広い記録・会話を扱うため、贈った相手、品物、反応を必ず結び付ける設計を採る理由は小さいと考える。これは既存サービスに関する仮説である。Giftoryでは身近な利用者を継続して観察し、実際に見返す項目だけを残す。記録が増えたときに翌年も使いたいと感じるかを確かめる。

## 3. 業務要件

| 場面 | 利用者の行動 | 終了時の状態 |
|---|---|---|
| 贈った直後 | 贈り主がログインし、贈った相手を選ぶ。初めてなら相手を登録し、品物を記録する | その相手の履歴に新しい記録が1件増える |
| 後日、感想を聞いたとき | 登録者が自分の記録に相手の言葉や使い方を追記する | 次回に品物と反応をまとめて読める |
| 次の誕生日・記念日の前 | 相手の履歴を開き、前回贈った品や喜ばれた点を確認する | 利用者が次の候補を比較できる |
| 夫婦・友人で選ぶとき（共有案） | 管理者が相手名と範囲を確認して招待し、受け手がログイン後に参加を確定する | 双方が当該相手の過去・今後の記録を確認・追加できる |

## 4. 機能要件

優先度の「必須」は個人利用版の範囲、「応用」はその完成後に取り組む共有機能の案を示す。応用を採用する場合は、招待・解除・アクセス制御を一組で実装する。

| ID | 優先度 | 機能と完了条件 |
|---|---|---|
| FN001〜FN005 | 必須 | 会員登録。名前・メール・パスワード・確認を受け付け、重複メールや不一致は日本語で表示する。通常登録はPG03へ進む。共有採用時に招待から登録した場合はPG11へ戻り、参加ボタンで所属を確定する |
| FN006〜FN010 | 必須 | ログイン・ログアウト。未認証で保護された画面・APIを利用できず、ログアウト後は再認証が必要 |
| FN011〜FN013 | 必須 | 相手一覧・登録。名前またはニックネームと関係性は必須、好みは任意。0件なら登録を案内する |
| FN014〜FN016 | 必須 | 相手詳細・編集・削除。PG06の履歴に贈った日・品物名・反応を表示し、反応が空なら「反応は未記入」と表示する。履歴は贈った日が新しい順、同日は記録IDの降順。相手の編集・削除は管理者のみ。削除は記録と参加者がともに0件の場合に限る案 |
| FN017〜FN019 | 必須 | 贈り物登録・入力検証。品物名、当日以前の贈った日、贈った人は必須。写真1枚（JPEG／PNG・2 MiB（2,097,152バイト）以下）、価格（0円以上の整数）、イベント、反応は任意 |
| FN020〜FN022 | 必須 | 贈り物詳細・編集・削除。贈った人と登録者を区別して表示し、登録者は写真の差し替え・削除や反応の追記ができる。記録削除は確認後に行う |
| FN023〜FN026 | 応用 | 相手単位のメンバー表示・招待発行・無効化・メンバー解除。招待は7日・1回限りとし、再発行で旧リンクを無効にする案。管理者はPG10を開き直しても有効な招待の期限を確認し、無効化できる。平文の招待URLは発行時だけ表示する |
| FN027〜FN030 | 応用 | 招待確認・参加、退出確認・実行、共有権限。招待経由の認証後は参加確認へ戻る。退出・解除後は元の投稿も閲覧・変更不可。投稿は残し、新しい招待で再参加した場合は自分の投稿を再編集できる案 |

| 画面ID | 画面名 |
|---|---|
| PG01・PG02 | 会員登録／ログイン |
| PG03〜PG06 | 相手一覧（ホーム）／相手登録／相手編集／相手詳細・贈り物履歴 |
| PG07〜PG09 | 贈り物登録／贈り物詳細／贈り物編集 |
| PG10〜PG12（応用） | 共有管理／招待の確認・参加／共有からの退出確認 |

個人利用版はユーザー・贈る相手・贈り物の3業務テーブルとPG01〜PG09で完結する。共有採用時に共有メンバー・招待の2テーブル、PG10〜PG12、PG06の共有管理ボタンを追加する。贈る相手は会員アカウントと独立する。「贈った人」は「夫婦」などを表せる自由入力、「登録者」はログインした会員から自動設定する。

画面はJavaScriptフレームワークで作成し、LaravelのAPIを通じて認証・登録・一覧・更新・削除を行う。画像取得もAPI側で認可する。初期版で商品カタログや配送サービスなどの外部APIとの連携は予定していない。

## 5. 非機能要件

- **権限と写真**　管理者は相手の登録者。個人用の記録と写真は本人だけが閲覧する。共有後はその相手の管理者と現在の参加者だけが閲覧・追加でき、投稿の編集・削除には登録者の一致も必要とする。APIは直接URLを指定された場合にも同じ判定を行う。
- **個人データ**　相手にはニックネームを使える。写真は非公開領域に置き、恒久的な公開URLを発行しない。公開リポジトリのサンプルやテストアカウントには架空の名前と記録を使う。
- **操作性**　スマートフォンで登録・閲覧・編集を完了できる。必須項目と任意項目を区別し、入力エラーは日本語で該当箇所に表示する。再送信時は通常の入力値を保持する。
- **性能・運用**　PG06では写真を取得せず、PG08では選んだ記録の写真だけを取得する。PG09では編集中の記録の写真を確認できる。履歴件数が増えた場合も必要な範囲を表示する。公開先の容量・休止条件を確認し、試用前と面談前に第三者としてHTTPSのURLを開き、ログインから主要操作まで確認する。

## 6. 制約条件

- 期間は8週間。第2週末までに公開GitHubリポジトリのURLをLMSへ提出する。初回レビュー後に要件を見直し、第3週に設計、第4〜7週に実装・公開、第7〜8週に検証を行う。
- リポジトリ名は giftory。ルートにPHP／LaravelのAPIとテスト、frontend/ にJavaScriptフレームワークの画面を配置する。フレームワークの具体名とAPI認証方式は設計時に選定する。DBはMySQLを予定し、テストはSQLiteのインメモリDBで動かす。
- API・フロントエンド・DBを自分名義の環境で構築し、第三者がHTTPSで利用できる状態にする。公開先の選定条件は2.5のとおり。秘密情報や実在する人の贈答記録はコミットしない。
- 認証保護と中心機能に、期待結果を検証するFeatureテストを用意する。Laravel Pintを通し、作業の区切りごとに変更内容が分かるコミットを残す。
- Claude Codeを利用し、自分の言葉でCLAUDE.mdを書く。生成されたコードや文書を確認し、技術選定、認証処理、アプリ内で最も長いメソッドを説明できるようにする。

## 7. スコープ外

| 対象外とすること | 理由 |
|---|---|
| 検索・絞り込み、誕生日通知、次に贈りたい候補リスト | まず相手別の履歴で過去の品を探せるかを確認する。記録件数や試用結果に応じて再検討する |
| 商品購入・配送・店舗連携、全体公開・SNS投稿 | 目的は個人または招待した相手との振り返りであり、贈答の手配や発信は対象としない |
| 管理者の退出・権限譲渡、アカウント削除（初期案） | 共同の記録を誰が管理し、どの投稿を残すかの決定が必要。最初の試用では参加者の退出・解除までを扱う |
